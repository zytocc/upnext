# Releases

A release is a `v*` tag on `main`. The tag starts two workflows: `release` (`.github/workflows/release.yml`, generated by [dist](https://github.com/axodotdev/cargo-dist), formerly cargo-dist, with hand edits its header lists) builds the Linux archives for x86_64 and arm64, the Windows x86_64 zip, the Windows installer, the Debian and Fedora packages and the Arch package with its `PKGBUILD` (and, once turned on, the Android app and the Flatpak bundle), each package with its SHA-256 checksum, publishes the GitHub release with the tag's CHANGELOG section as its notes, and then pushes the packages to the apt and dnf repositories on Cloudsmith once those are set up; `docker` pushes the image as the version and `latest`.

The Linux archives (`upnext-x86_64-unknown-linux-gnu.tar.xz` and `upnext-aarch64-unknown-linux-gnu.tar.xz`, the second built natively on GitHub's `ubuntu-22.04-arm` runner) hold `upnext` and `upnext-app`, built with the default features and the web UI inside, plus the README, the CHANGELOG, both licences, the third-party notices (`THIRD_PARTY_NOTICES.txt`, [Third-party notices](#third-party-notices)), `upnext.service` (the systemd user service), and `upnext.desktop` and `icons/hicolor/` (the launcher entry and its icons, which the Arch package installs from the archive). They're built on Ubuntu 22.04, so they run on glibc 2.35 or newer, and they need WebKitGTK 4.1 and GTK 3 at run time (the README's "From a release (other Linux)" says how to install them).

The packages aren't dist's (dist makes no `.deb` or `.rpm`): the workflow's `build-linux-packages` job unpacks both Linux archives and runs `contrib/linux/build-packages.sh` on their programs, which repacks them with [nfpm](https://nfpm.goreleaser.com) 2.47.0 (downloaded and checked against its SHA-256) from `contrib/linux/nfpm.yaml`: `upnext_<version>-1_amd64.deb`, `upnext_<version>-1_arm64.deb`, `upnext-<version>-1.x86_64.rpm` and `upnext-<version>-1.aarch64.rpm`, each with a `.sha256`. Before anything is published, `contrib/linux/smoke-test.sh` installs the amd64 packages in `debian:12`, `ubuntu:24.04` and `fedora:44` containers, runs `upnext --version`, `upnext doctor` and `upnext serve`, and removes them again; a failure there stops the release. The `publish-cloudsmith` job then pushes the four packages to Cloudsmith ([The package repository](#the-package-repository)); it skips prereleases, and does nothing until the repository is set up.

The Arch package isn't dist's either: the workflow's `build-arch-package` job runs `contrib/arch/build-package.sh`, which writes the release's `PKGBUILD` with `contrib/arch/render-pkgbuild.sh` (the template `contrib/arch/upnext-bin/PKGBUILD` with the tag, the version and both Linux archives' SHA-256 filled in; `v0.2.0-rc.1` becomes the version `0.2.0rc.1`, which pacman sorts before `0.2.0`), puts the x86_64 archive beside it under the name its source line gives, and runs makepkg as an unprivileged user in an `archlinux:base-devel` container. makepkg checks that archive against the checksum instead of downloading it, so the package is built from the very `PKGBUILD` the release publishes. namcap then checks the `PKGBUILD` and the package, and any error it reports stops the release; `contrib/linux/smoke-test.sh` installs the package in a fresh `archlinux:latest` container after `pacman -Syu`, runs the same checks as for the other packages and removes it again. The release gets `upnext-bin-<pkgver>-1-x86_64.pkg.tar.zst` with its `.sha256`, and `PKGBUILD`, which also builds on aarch64 from the arm64 archive. The job uses no secrets. Once the signing key is set up ([The Arch package repository](#the-arch-package-repository)), the `sign-pacman-repo` job signs that package and adds the signed repository database beside it, so `pacman -Syu` brings each release; until then neither is signed and there's no database.

The Windows zip (`upnext-x86_64-pc-windows-msvc.zip`) holds `upnext.exe` and `upnext-app.exe`, built by dist on GitHub's Windows Server 2022 runner with MSVC, and the same other files (`upnext.service`, `upnext.desktop` and the icons too: dist's `include` applies to every archive). The installer (`upnext-x86_64-pc-windows-msvc.msi`) isn't dist's: the workflow's `build-msi` job unpacks that zip on `windows-latest` and runs `contrib/windows/build-msi.ps1` on the two exes, which builds the per-user MSI from `contrib/windows/upnext.wxs` with WiX 3.14.1 (`contrib/windows/README.md`). Neither is signed yet: signing waits on SignPath Foundation's acceptance (the README's [Code signing policy](../../README.md#code-signing-policy)), and then the two exes go through SignPath between the unzip and the MSI, and the MSI after it. The Microsoft Store package, from the same zip, needs none: the Store signs it ([The Microsoft Store package](#the-microsoft-store-package)). The release notes end with a link to that policy, which the host job adds.

## Third-party notices

`THIRD_PARTY_NOTICES.txt`, at the repository's root, is what the licences of everything built into UpNext ask to be passed on with it. It lists every Rust crate built into the two programs and every npm package built into the web UI, with its version, licence and its page on crates.io or npm; the two things kept by hand, Microsoft's WebView2 loader (linked into the Windows programs) and tini (in the container image); the game data sources from `web/src/lib/credits.ts`; and then each licence, copyright and notice text those name, once, with every package that uses it. `android/app/src/main/assets/third_party_notices.txt` does the same for the Android app's libraries, which are all Apache-2.0. `docs/THIRD_PARTY.md` stays the human-readable summary of the services UpNext talks to.

Both files are generated by `contrib/notices/generate.mjs` and committed, because the Flatpak builds with no network and every other artefact copies the committed file:

- **Crates.** [cargo-about](https://github.com/EmbarkStudios/cargo-about) 0.9.2, with `contrib/notices/about.toml`, lists the crates the release targets (Linux x86_64 and arm64, Windows x86_64, with the default features) build into the programs, leaving out build and development dependencies, and picks one licence from each crate's SPDX expression in the order `about.toml` gives (MIT first). The script takes each crate's own licence, copyright and notice files from cargo's download folder, apart from the text of an alternative licence it wasn't picked under, and cargo-about's standard text for a licence the crate has no file for. Where that standard text is a template (MIT's "Copyright (c) <year> <copyright holders>"), the crate's real copyright lines come from `contrib/notices/copyrights.txt`, taken from the licence file in the crate's repository at the commit it was published from; the script stops when a crate needs lines that aren't there. It also stops unless `cargo about --version` is 0.9.2.
- **npm packages.** Every package `web/package-lock.json` doesn't mark as a development one, plus Vite and Tailwind, whose code goes into the built UI, with the licence files in `web/node_modules`. The three fonts come with their packages, each with the SIL Open Font License and its copyright line.
- **Kept by hand**, in the script's `HAND` list, and pinned: the WebView2 loader is the `WebView2LoaderStatic.lib` that `webview2-com-sys` carries, byte for byte the one in Microsoft's `Microsoft.Web.WebView2` NuGet package 1.0.3800.47, whose `LICENSE.txt` (a BSD-3-Clause-style licence) and `NOTICE.txt` are in `contrib/notices/webview2/`; the script checks the library's SHA-256. tini's MIT licence is in `contrib/notices/tini/`, checked against the version the `Dockerfile` downloads. The Android list (`ANDROID`) reads its versions from `libs.versions.toml` and stops on a library it doesn't list.

To regenerate, after any change to `Cargo.lock`, `web/package-lock.json`, `android/gradle/libs.versions.toml` or `credits.ts`:

```sh
cargo install --locked cargo-about --version 0.9.2 --features cli   # once
cargo fetch --locked
(cd web && npm ci)
node contrib/notices/generate.mjs
```

and commit both files with the change. With `--check` the script compares instead of writing. The `notices` workflow (`.github/workflows/notices.yml`) runs that on every change to what goes in, and the release's `check-notices` job runs it on the tag; the host job doesn't publish a release whose notices differ. The container image that the `docker` workflow pushes on the same tag doesn't wait for that job, which keeps that workflow to building and testing the image: it trusts the `notices` workflow, which has run on every commit that changed what goes into the notices, so step 4 of [Releasing a version](#releasing-a-version) checks that its latest run on `main` passed. A Dependabot update of a crate or an npm package fails `notices` until someone runs the lines above on its branch and pushes the result. When a pinned entry changes (a new `webview2-com-sys`, tini or zxing-android-embedded), the script stops and says what to look at: for the loader, download the `Microsoft.Web.WebView2` package whose version is the new DLL's file version from `api.nuget.org/v3-flatcontainer/microsoft.web.webview2/`, check that its `build/native/x64/WebView2LoaderStatic.lib` has the crate's SHA-256, and replace the version, the hash and the two files. cargo-about's version goes up only with a regeneration, since it words some standard texts.

Where each artefact carries it, beside `LICENSE-MIT` and `LICENSE-APACHE`:

| Artefact | Where | Checked by |
|---|---|---|
| Linux archives and Windows zip | the top folder (dist's `include`) | by hand, in [Checking a release](#checking-a-release) |
| MSI | `%LOCALAPPDATA%\Programs\UpNext` | `build-msi.ps1` stops without it |
| `.deb` | `/usr/share/doc/upnext/` | `contrib/linux/smoke-test.sh` (the package's file list) |
| `.rpm` | `/usr/share/licenses/upnext/`, as a licence file | the same |
| Arch package | `/usr/share/licenses/upnext-bin/` | the same |
| Container image | `/usr/share/doc/upnext/` | `contrib/docker/smoke-test.sh` |
| Flatpak | `/app/share/licenses/io.github.zytocc.UpNext/` | `contrib/flatpak/smoke-test.sh` |
| Steam depots | both depots' top folder; the Linux one's bundled libraries keep theirs in `share/licenses/` | `bundle-linux.py`, `build-depots.sh` and `contrib/steam/smoke-test.sh` |
| APK | `assets/third_party_notices.txt`, shown by "Open-source licences" on the first screen | none yet: the release's Gradle build packs whatever is in `assets/` |

Every build of the programs also serves the file at `/third-party-notices.txt` (`src/server/ui.rs`, open to any device like the UI's own files), which Settings › About links to, and the smoke tests of the packages, the image and the Flatpak fetch it.

## Releasing a version

1. On an up-to-date `main` with CI green: set `version` in `Cargo.toml`, then `cargo check` to update `Cargo.lock` and `UPNEXT_UPDATE_OPENAPI=1 cargo test --locked openapi` to update `docs/openapi.json`, which carries the version too. Set the Android app's `versionName` to the same version and `versionCode` to major × 1,000,000 + minor × 1,000 + patch in `android/app/build.gradle.kts` (`cd android && ./gradlew :app:checkVersion` checks both), and add `android/fastlane/metadata/android/en-US/changelogs/<versionCode>.txt` with a line or two for F-Droid.
2. In `CHANGELOG.md`, turn `## [Unreleased]` into `## [X.Y.Z] - YYYY-MM-DD` with that day's date, and start a new empty `## [Unreleased]` above it (for 0.1.0, fold it into the existing section instead, as "Going public" step 2 says). In `contrib/flatpak/io.github.zytocc.UpNext.metainfo.xml`, add `<release version="X.Y.Z" date="YYYY-MM-DD">` with a line on what's new at the top of `<releases>` (the 0.1.0 line's date becomes the day it's tagged), and check it with `appstreamcli validate --no-net` on that file.
3. Preview what the release will say and build: `dist plan --tag=vX.Y.Z` lists the files, and `dist build --tag=vX.Y.Z` builds the archive for the machine it runs on into `target/distrib/` (build `web/dist` first: `cd web && npm ci && npm run build`). To try the MSI, build it on a Windows machine and run through "Checking an MSI" in `contrib/windows/README.md`. To try the Linux packages, build them from a release build on Linux (`cargo build --release --locked --bins`, then `contrib/linux/build-packages.sh --bin-dir target/release`, which writes them to `target/linux-packages`) and run `contrib/linux/smoke-test.sh` on each, as the workflow does (its comment has the command); it needs docker. To try the Arch package, run `contrib/arch/build-package.sh --tag vX.Y.Z --dist-dir target/distrib` after `dist build`, which writes it and the `PKGBUILD` to `target/arch-package`, then the smoke test in `archlinux:latest`; it needs docker and Arch's mirrors, and on Arch itself `--host` builds with the machine's makepkg instead (the script's comment has the options).
4. Commit, push, and wait for `ci` to pass on that commit. Check too that the `notices` workflow's latest run on `main` passed (it runs when a commit changes what goes into the notices; run it by hand from the Actions tab if unsure), since the container image the tag publishes relies on it ([Third-party notices](#third-party-notices)).
5. Tag and push the tag. A tag records who made it and when, and it is public: make it in a clone whose `user.name` and `user.email` are the GitHub account's name and noreply address (`git config user.name` and `git config user.email` in that clone), and with `TZ=UTC`, so the date is `+0000` like the commits':

   ```sh
   git config user.email                        # the noreply address
   TZ=UTC git tag -a vX.Y.Z -m "UpNext X.Y.Z"
   git for-each-ref refs/tags/vX.Y.Z --format='%(taggername) %(taggeremail) %(taggerdate:iso)'
   git push origin vX.Y.Z
   gh run watch "$(gh run list --workflow release.yml --limit 1 --json databaseId --jq '.[0].databaseId')"
   ```

6. Check the release page: the two Linux archives, the Windows zip, the MSI, the four Debian and Fedora packages and the Arch package, each with its `.sha256`, the `PKGBUILD`, `sha256.sum` and the source archive are attached; once the Arch signing key is set up, also the Arch package's `.sig`, `upnext.db`, `upnext.files`, their two `.sig` files and `upnext-signing-key.asc` (until the `PACMAN_KEY_FINGERPRINT` variable is set, the run's `sign-pacman-repo` job only leaves a notice saying the repository wasn't published); once the Android release key is set up, `upnext-android-X.Y.Z.apk` and its `.sha256` (until then the `build-apk` job leaves a notice instead); once the Flatpak bundle is turned on, `upnext-X.Y.Z-x86_64.flatpak` and its `.sha256` (until then the `build-flatpak` job is skipped and the host job leaves a notice instead). The Microsoft Store package isn't a release file: once its variables are set, it is the run's `msix` artifact, which [The Microsoft Store package](#the-microsoft-store-package) says how to submit. The Steam copy's depots aren't release files: once they are turned on, they are the run's `steam-depots` artifact, the release gains `upnext-steam-linux-sources.tar` and its `.sha256` (the source of the Linux depot's libraries), and [The Steam copy](#the-steam-copy) says what to check. `sha256.sum` lists dist's files, not the MSI or the packages, which have only their own `.sha256`. The run's `publish-cloudsmith` job either pushed the four packages (its log names each one's page on Cloudsmith), or is skipped: for a prerelease, or while the repository variable isn't set; with the variable set and no secret, it says so in a notice. Then follow [Checking a release](#checking-a-release).
7. Before announcing the release, submit the Windows files to Microsoft, so Defender's machine-learning detections (names ending `!ml`, such as `Wacatac!ml`) don't flag them: at [Microsoft's file submission page](https://www.microsoft.com/en-us/wdsi/filesubmission), sign in with a Microsoft account, choose "Software developer", and submit the MSI, then `upnext.exe` and `upnext-app.exe` from the zip, one submission each, for Microsoft Defender Antivirus, saying the file is clean (or incorrectly detected, if Defender already flags it), with the release page's link and the file's SHA-256 in the details. Each submission's page shows Microsoft's answer when it comes. Do this for every release: each one's files are new to Microsoft.
8. Open the pull request that brings the release to winget, as [winget](#winget) says. The Linux one-line installer (`site/install.sh`) needs nothing: it installs whichever release is newest.

A tag like `v0.2.0-rc.1` makes a prerelease. dist releases only a crate whose version is the tag's, and stops with "This workspace doesn't have anything for dist to Release!" otherwise, so step 1 sets the version to `0.2.0-rc.1` for that tag (`versionCode` is the same as 0.2.0's, since the suffix doesn't count), and a commit of its own sets it back to `0.2.0` before the final tag. A prerelease's notes are the `## [0.2.0]` section of `CHANGELOG.md`, which dist uses when the changelog has no section for the prerelease itself (without one, the notes are empty), so step 2 is done for the first candidate and the changelog needs no heading per candidate. Its MSI has the version without the suffix (0.2.0), since Windows Installer takes numbers only. To change dist's settings, edit `dist-workspace.toml` (or `.github/build-setup.yml`, the steps that build the web UI first), then regenerate the workflow and commit it with them: `allow-dirty = ["ci"]` in that file (there so Dependabot's action bumps in `release.yml` don't fail the release) also stops `dist generate` from rewriting `release.yml`, so comment that line out, run `dist generate`, and put it back, with the hand edits `release.yml`'s header lists (the `build-msi`, `build-msix`, `build-linux-packages`, `publish-cloudsmith`, `build-arch-package`, `sign-pacman-repo`, `build-apk`, `build-flatpak`, `build-steam-depots`, `attach-steam-sources`, `publish-steam` and `check-notices` jobs among them). `dist init` upgrades dist itself.

## Checking a release

On a machine that has never built UpNext and has no Rust or Node:

```sh
V=X.Y.Z
curl -LO "https://github.com/zytocc/upnext/releases/download/v$V/upnext-x86_64-unknown-linux-gnu.tar.xz"
curl -LO "https://github.com/zytocc/upnext/releases/download/v$V/upnext-x86_64-unknown-linux-gnu.tar.xz.sha256"
sha256sum -c upnext-x86_64-unknown-linux-gnu.tar.xz.sha256
tar xf upnext-x86_64-unknown-linux-gnu.tar.xz
```

The folder has `THIRD_PARTY_NOTICES.txt` beside the licences. Then follow the README's "From a release" as written: install the two libraries, put the binaries on the `PATH`, run `upnext --version` (it must print the version), `upnext doctor`, and `upnext serve`, and open `http://127.0.0.1:8787`: the setup page must load (it's the embedded UI, not the "this build has no web UI" placeholder), and Settings › About's "third-party notices" link must open the notices. `upnext app` opens the window. Use `UPNEXT_DATA_DIR` pointed at an empty folder if the machine already has an UpNext database.

On a Windows 11 machine, in PowerShell:

```powershell
$V = "X.Y.Z"
$base = "https://github.com/zytocc/upnext/releases/download/v$V"
Invoke-WebRequest -OutFile upnext-x86_64-pc-windows-msvc.msi "$base/upnext-x86_64-pc-windows-msvc.msi"
Invoke-WebRequest -OutFile upnext-x86_64-pc-windows-msvc.msi.sha256 "$base/upnext-x86_64-pc-windows-msvc.msi.sha256"
(Get-FileHash upnext-x86_64-pc-windows-msvc.msi).Hash.ToLower()   # the same as the first word of:
Get-Content upnext-x86_64-pc-windows-msvc.msi.sha256
```

Then install it and go through "Checking an MSI" in `contrib/windows/README.md` from step 1. A browser download, unlike `Invoke-WebRequest`, marks the file as from the internet, which is what brings up SmartScreen; download it once that way too and check the README's Windows section says what happens.

For the Linux packages, on a Debian, Ubuntu or Fedora desktop, or in [distrobox](https://distrobox.it) boxes of `debian:13`, `ubuntu:24.04` and `fedora:44` on another distribution (they share the display and the home folder, so set `UPNEXT_DATA_DIR` to an empty folder there):

```sh
V=X.Y.Z
base="https://github.com/zytocc/upnext/releases/download/v$V"
# Debian and Ubuntu (arm64: _arm64.deb)
curl -LO "$base/upnext_$V-1_amd64.deb" -LO "$base/upnext_$V-1_amd64.deb.sha256"
sha256sum -c "upnext_$V-1_amd64.deb.sha256" && sudo apt install "./upnext_$V-1_amd64.deb"
# Fedora (arm64: .aarch64.rpm)
curl -LO "$base/upnext-$V-1.x86_64.rpm" -LO "$base/upnext-$V-1.x86_64.rpm.sha256"
sha256sum -c "upnext-$V-1.x86_64.rpm.sha256" && sudo dnf install "./upnext-$V-1.x86_64.rpm"

upnext --version          # X.Y.Z
upnext doctor
upnext app                # the window
sudo apt remove upnext    # or: sudo dnf remove upnext; the data folder stays
```

On a desktop (not a box), UpNext is in the launcher under Games with its icon, and `systemctl --user enable --now upnext` starts the service. Once the package repository is set up, check it the same way with `sudo apt install upnext` or `sudo dnf install upnext` after the README's repository lines, and that the next release arrives through `sudo apt update && sudo apt upgrade` or `sudo dnf upgrade`.

For the Arch package, on an Arch desktop (or a distrobox box of `archlinux:latest`, with `UPNEXT_DATA_DIR` set to an empty folder), both ways the README's "Arch Linux" gives:

```sh
V=X.Y.Z
base="https://github.com/zytocc/upnext/releases/download/v$V"
mkdir upnext-bin && cd upnext-bin
curl -fsSLO "$base/PKGBUILD"
makepkg -si                       # downloads the archive, checks it, installs upnext-bin
upnext --version                  # X.Y.Z
upnext doctor
upnext app                        # the window
sudo pacman -R upnext-bin         # the data folder stays
curl -fsSLO "$base/upnext-bin-$V-1-x86_64.pkg.tar.zst" -LO "$base/upnext-bin-$V-1-x86_64.pkg.tar.zst.sha256"
sha256sum -c "upnext-bin-$V-1-x86_64.pkg.tar.zst.sha256" && sudo pacman -U "./upnext-bin-$V-1-x86_64.pkg.tar.zst"
```

For a prerelease the file name has the version without its hyphen (`0.2.0rc.1`). On a desktop, UpNext is in the launcher under Games with its icon, a Steam game launches from it, and `systemctl --user enable --now upnext` starts the service. On a machine that had a `cargo install` copy, the README's steps replace it without touching the library.

Once the Arch package repository is set up, check it too, as [The Arch package repository](#the-arch-package-repository) describes under "On each release".

## The package repository

The `.deb` and `.rpm` packages also go to an apt and a dnf repository hosted by [Cloudsmith](https://cloudsmith.com), free for open-source projects, so `apt upgrade` and `dnf upgrade` bring new versions. Nothing is pushed until the steps below are done, and the release workflow skips the push cleanly until then. The free plan needs a public repository with an SPDX licence and a credit in the README, so this is set up after the repository goes public; `<owner>` and `<repo>` below are the Cloudsmith account and repository names chosen in step 1 (the examples assume `upnext` for the repository).

### Setting it up (once)

1. **The account and repository.** Sign up at Cloudsmith, create an organization (`<owner>`), and apply for [open-source hosting](https://docs.cloudsmith.com/open-source-hosting-policy) with the GitHub repository's link and its licence (MIT OR Apache-2.0). Once it's granted, create a public repository `<repo>` under that plan. Cloudsmith signs the repository's metadata with a key of its own; nothing to generate.
2. **A service account for CI.** In the organization, Services, create one (for example `upnext-ci`) with write access to `<repo>` alone, and copy its API key. It's used for nothing else.
3. **The secret and the variable**, in the GitHub repository:

   ```sh
   gh secret set CLOUDSMITH_API_KEY --repo zytocc/upnext          # paste the service account's key
   gh variable set CLOUDSMITH_REPOSITORY --repo zytocc/upnext --body "<owner>/<repo>"
   ```

   The `publish-cloudsmith` job runs only when `CLOUDSMITH_REPOSITORY` is set, and without the secret it stops with a notice; neither is read by any other job.
4. **The packages already released.** The job runs on the next tag. To publish the current release's packages now, re-run that tag's release run's `publish-cloudsmith` job (`gh run rerun <run id> --job <job id>`; `gh run view <run id>` lists the jobs), or upload the four files from the release page in Cloudsmith's web app, each to the distribution `any-distro/any-version`.
5. **The README.** Under "Debian, Ubuntu and Fedora", replace the closing sentence about a planned repository with the lines below, after checking them against the repository's "Set Me Up" page in Cloudsmith (Debian and RedHat tabs, with "any-distro" and "any-version"), which has the exact key and source URLs for the account:

   ````markdown
   To get new versions with the rest of your updates, add UpNext's package repository instead, then install `upnext` from it. On Debian and Ubuntu:

   ```sh
   curl -fsSL 'https://dl.cloudsmith.io/public/<owner>/<repo>/gpg.key' | sudo gpg --dearmor -o /usr/share/keyrings/upnext-archive-keyring.gpg
   echo 'deb [signed-by=/usr/share/keyrings/upnext-archive-keyring.gpg] https://dl.cloudsmith.io/public/<owner>/<repo>/deb/any-distro any-version main' | sudo tee /etc/apt/sources.list.d/upnext.list
   sudo apt update && sudo apt install upnext
   ```

   On Fedora:

   ```sh
   curl -fsSL 'https://dl.cloudsmith.io/public/<owner>/<repo>/config.rpm.txt?distro=any-distro&codename=any-version' | sudo tee /etc/yum.repos.d/upnext.repo
   sudo dnf install upnext
   ```

   Package repository hosting is provided free by [Cloudsmith](https://cloudsmith.com).
   ````

   Add their badge beside the credit too if the open-source agreement asks for one.

### On each release

Nothing by hand: `publish-cloudsmith` pushes the four packages after the GitHub release is published, and its log names each package's page. A prerelease (`v0.2.0-rc.1`) is never pushed, so testers install those from the release page. Then check one install from the repository, as in [Checking a release](#checking-a-release). Cloudsmith processes each package after the push (it indexes and signs it), and one that fails there shows the reason on its page. It refuses a package whose name and version it already has, so a re-run after a partial push fails on the ones that made it: delete those in the web app first, or upload the rest there.

If the API key leaks or its holder changes, make a new one for the service account in Cloudsmith, set it with `gh secret set CLOUDSMITH_API_KEY` again, and revoke the old one. To stop publishing, delete the `CLOUDSMITH_REPOSITORY` variable.

## The Arch package repository

UpNext's pacman repository is a few files on each release: the Arch package and its signature (`upnext-bin-<pkgver>-1-x86_64.pkg.tar.zst.sig`), the database `upnext.db` listing that one package with its signature inside, the file list `upnext.files` that `pacman -F` reads, a signature for each of those two, and the public key `upnext-signing-key.asc`. Users add `Server = https://github.com/zytocc/upnext/releases/latest/download` to `pacman.conf`, which GitHub redirects to the newest release that isn't a prerelease, so each stable release replaces the repository for everyone at once and `pacman -Syu` brings it. The release workflow's `sign-pacman-repo` job writes the files with `contrib/arch/sign-repo.sh` (its comment has the details) after `build-arch-package`, and `host` attaches them with everything else.

One key signs everything: an ed25519 primary key that only certifies and stays offline on a USB stick, and a signing subkey that expires after two years and is the only part the workflow ever holds. Users trust the primary key (`pacman-key --lsign-key`), so the subkey can be renewed or replaced without them signing anything again; they only re-import the key file. The job signs only when the repository variable `PACMAN_KEY_FINGERPRINT` is set (otherwise it leaves a notice that the repository wasn't published), and then it needs the `PACMAN_SIGNING_KEY` secret (the subkey) and, if the subkey has a passphrase, `PACMAN_SIGNING_KEY_PASSPHRASE`. It refuses to sign with a key whose fingerprint isn't the variable's or that isn't the committed `contrib/arch/upnext-signing-key.asc`, and it refuses a secret that holds the primary key's secret half. Without the secret it fails and the release with it: once people have the `[upnext]` stanza, a release without `upnext.db` would break their `pacman -Syu`.

### Making the signing key (once)

On a Linux machine with GnuPG 2.2 or newer, `gh` signed in to GitHub, and a checkout of the repository (`~/src/upnext` below). The key lives on a USB stick, never on the computer's disk; an encrypted one (LUKS) is better. Mounted at `/run/media/you/KEYS` below:

1. **Make the key** in a keyring of its own on the stick. gpg asks for a passphrase for it; pick a long one and keep it in your password manager.

   ```sh
   export GNUPGHOME=/run/media/you/KEYS/upnext-gnupg
   mkdir -m 700 "$GNUPGHOME"
   gpg --quick-generate-key 'UpNext package signing' ed25519 cert never
   FPR=$(gpg --list-keys --with-colons 'UpNext package signing' | awk -F: '$1 == "fpr" {print $10; exit}')
   gpg --quick-add-key "$FPR" ed25519 sign 2y
   gpg -K                 # sec ed25519 [C], and one ssb ed25519 [S] expiring in two years
   echo "$FPR"            # the fingerprint: 40 hexadecimal characters
   ```

   The user id has no email address on purpose; nothing else asks for one. The primary key doesn't expire, since renewing it would mean every user re-importing it; it is protected by staying offline, and by the revocation certificate below if it's ever lost or exposed.

2. **Back it up:** copy the whole `upnext-gnupg` folder to a second stick kept somewhere else. gpg also wrote a revocation certificate for the primary key, `upnext-gnupg/openpgp-revocs.d/<fingerprint>.rev`; print it or keep a third copy apart from both sticks, since it's what withdraws the key if the sticks are lost.

3. **Give the workflow the subkey**, never the primary key. `--export-secret-subkeys` exports the subkey's secret half and only a stub of the primary's (gpg asks for the passphrase):

   ```sh
   gpg --armor --export-secret-subkeys "$FPR" | gh secret set PACMAN_SIGNING_KEY --repo zytocc/upnext
   gh secret set PACMAN_SIGNING_KEY_PASSPHRASE --repo zytocc/upnext      # paste the key's passphrase
   ```

   The secrets do nothing yet: the variable that turns the repository on comes in step 5, once the public key is on `main`.

4. **Publish the public key:** export it over the placeholder and print the fingerprint the way gpg groups it.

   ```sh
   gpg --armor --export-options export-minimal --export "$FPR" > ~/src/upnext/contrib/arch/upnext-signing-key.asc
   gpg --fingerprint "$FPR"
   ```

   Then put the README lines below into the README's "Arch Linux" section, in place of the sentence that says the repository's lines will be here, with `<FINGERPRINT>` replaced by the fingerprint (no spaces), and commit both files to `main`. Or hand the `.asc` file and the fingerprint to a session to commit; neither is secret.

5. **Turn the repository on,** only once that commit is on `main`: the job checks the key against the committed file, so a tag pushed while the placeholder is still there would fail.

   ```sh
   gh variable set PACMAN_KEY_FINGERPRINT --repo zytocc/upnext --body "$FPR"
   ```

6. **Put the stick away:** `unset GNUPGHOME`, unmount it, and store it offline. Nothing on the computer holds the key.

7. **Try it on a prerelease** before the next stable tag: tag `vX.Y.Z-rc.1`, check that its release has the files listed above, then on an Arch machine or in an `archlinux:latest` container follow the README lines with `Server = https://github.com/zytocc/upnext/releases/download/vX.Y.Z-rc.1` instead of `latest/download`. `pacman -Sy` must sync without errors, and `sudo pacman -S upnext` must install `upnext-bin` with `pacman -Qi upnext-bin` saying "Validated By: Signature". (In a container, run `pacman-key --init` first: Arch's image ships without the local key every Arch install has.)

The README lines (the fence inside is the README's own):

````markdown
To get new versions with `pacman -Syu`, use UpNext's own pacman repository instead. Its packages and database are signed with UpNext's key, whose fingerprint is `<FINGERPRINT>`. Import the key, check that `pacman-key --finger` prints that fingerprint, and sign it locally so pacman trusts it:

```sh
curl -fsSLO https://raw.githubusercontent.com/zytocc/upnext/main/contrib/arch/upnext-signing-key.asc
sudo pacman-key --add upnext-signing-key.asc
sudo pacman-key --finger <FINGERPRINT>
sudo pacman-key --lsign-key <FINGERPRINT>
```

Then add these lines at the end of `/etc/pacman.conf` and run `sudo pacman -Syu upnext`:

```ini
[upnext]
SigLevel = Required
Server = https://github.com/zytocc/upnext/releases/latest/download
```

`SigLevel = Required` makes pacman check the signature on the database as well as on each package. Each release replaces the repository with its own version, so if `pacman -S` reports a 404 for an `upnext-bin` file, a new release came out since your last sync, and `sudo pacman -Syu` fixes it. If pacman says the key is unknown or has expired, the signing subkey was renewed: download `upnext-signing-key.asc` again and repeat `pacman-key --add`. With the key imported, `sudo pacman -U` also takes a release's package link directly, which is how to go back a version.
````

### On each release

Nothing by hand: `sign-pacman-repo` signs the package and builds the database, and `host` attaches the files. After a stable release, on an Arch machine with the repository set up, `sudo pacman -Syu` must offer the new `upnext-bin`, and `pacman -Qi upnext-bin` must say "Validated By: Signature" once it's installed. A prerelease carries the same files, reached only through a `Server` line naming its tag.

### Renewing the subkey

The subkey expires two years after it was made (`gpg -K` with the stick shows the date), and an expired subkey makes the job fail. A month or two before then, with the stick mounted and `FPR` set as in step 1:

```sh
export GNUPGHOME=/run/media/you/KEYS/upnext-gnupg
gpg --quick-set-expire "$FPR" 2y '*'
gpg --armor --export-secret-subkeys "$FPR" | gh secret set PACMAN_SIGNING_KEY --repo zytocc/upnext
gpg --armor --export-options export-minimal --export "$FPR" > ~/src/upnext/contrib/arch/upnext-signing-key.asc
```

Commit the new `.asc` and release soon after, with a line in the release notes asking Arch users to re-import the key file (the README's troubleshooting sentence covers anyone who misses it). The secret carries the subkey's public half too, which is why it is set again: the job refuses a subkey whose copy there has expired.

### If the subkey leaks

Revoke it and make a new one with the primary key, then publish both:

```sh
export GNUPGHOME=/run/media/you/KEYS/upnext-gnupg
gpg --edit-key "$FPR"       # at the prompt: key N (the subkey's place in the list, from 1), revkey, y, reason 1 (compromised), save
gpg --quick-add-key "$FPR" ed25519 sign 2y
```

then set the secret and export the public key as when renewing, commit, and release at once with a note in the release asking Arch users to re-import the key file; pacman then refuses anything signed by the revoked subkey. The job uses the newest signing subkey whose secret it was given. Older releases' packages were signed by the revoked subkey, so once the key file is re-imported pacman refuses their links (checked with a throwaway key); they still install as a downloaded file with `pacman -U ./<file>`, without the `.sig` beside it, since Arch's default `LocalFileSigLevel = Optional` doesn't ask for one.

If the primary key leaks, or both sticks are lost, import the revocation certificate in that keyring (gpg prefixes its `-----BEGIN` line with a colon so it can't be imported by accident: delete that colon, then `gpg --import <fingerprint>.rev`), export the public key over `upnext-signing-key.asc` so the revocation reaches users, make a new key from step 1, and tell Arch users in the release notes and the README to remove the old key (`sudo pacman-key --delete <old fingerprint>`) and set up the new one.

To stop publishing the repository, delete the `PACMAN_KEY_FINGERPRINT` variable, remove the README lines, and say in the next release notes that Arch users should remove the `[upnext]` stanza, since `pacman -Syu` fails for them once a release has no database.

### The Arch images

The Arch jobs run in `archlinux:base-devel` (the build) and `archlinux:latest` (the smoke test and the signing), pinned by digest like the actions, so a release builds and signs with the image it was tried with, and the signing key only ever meets code picked on purpose. The build and the smoke test run `pacman -Syu` first, so their packages are current anyway; the signing step uses the pinned image's gpg and repo-add as they are. Move the pins on every few months, and when Arch moves pacman to a new major version:

```sh
for tag in base-devel latest; do
  docker pull "archlinux:$tag" && docker image inspect --format '{{index .RepoDigests 0}}' "archlinux:$tag"
done
```

Each prints `archlinux@sha256:<digest>`; write it as `archlinux:<tag>@sha256:<digest>` in `contrib/arch/build-package.sh` (base-devel), `contrib/arch/sign-repo.sh` and the `ARCH_IMAGE` line of `release.yml`'s `build-arch-package` job (both latest). Then build a package with the new image as under [Releasing a version](#releasing-a-version), step 3, and sign it with a throwaway key: make one as in "Making the signing key" but in a temporary `GNUPGHOME` (`mktemp -d`), export its subkey and public key to files, and run `PACMAN_SIGNING_KEY="$(cat subkey.asc)" PACMAN_SIGNING_KEY_PASSPHRASE=… contrib/arch/sign-repo.sh --package <the package> --fingerprint "$FPR" --public-key public.asc`. Never commit a throwaway key.

## The Android app

The release workflow's `build-apk` job builds the Android app from `android/` on each tag, signs it with the release key and attaches `upnext-android-X.Y.Z.apk` and its `.sha256` to the release. Every APK must carry the same key, so each installs over the last, and F-Droid ships the same signature (`contrib/fdroid/`); a lost key means a new package name and every install removed and made again. Without the key the job leaves a notice and the release goes out without the APK.

### Making the release key (once)

On a computer you trust, with a JDK (`keytool`):

```sh
keytool -genkeypair -v -keystore upnext-release.jks -alias upnext -keyalg RSA -keysize 4096 -validity 10000 \
  -dname "CN=UpNext contributors"
keytool -list -v -keystore upnext-release.jks -alias upnext   # note the SHA-256 fingerprint
```

Keep `upnext-release.jks` and its passwords offline, with a backup somewhere else (an encrypted drive, a password manager's attachment). Then give it to the release workflow as four repository secrets, used on tags only:

```sh
R=zytocc/upnext
base64 -w0 upnext-release.jks | gh secret set UPNEXT_ANDROID_KEYSTORE --repo $R
gh secret set UPNEXT_ANDROID_KEYSTORE_PASSWORD --repo $R
gh secret set UPNEXT_ANDROID_KEY_ALIAS --repo $R --body upnext
gh secret set UPNEXT_ANDROID_KEY_PASSWORD --repo $R
```

The fingerprint (lowercase, without colons) goes in `AllowedAPKSigningKeys` in `contrib/fdroid/io.github.zytocc.upnext.yml`, and later in Google Play's App Signing as the app's own key, so all three carry one signature.

### Google's developer verification (once)

Certified Android devices install apps only from developers registered with Google, sideloaded APKs and other stores included: enforced from 30 September 2026 in Brazil, Indonesia, Singapore and Thailand, and worldwide from 2027 (news reports, re-checked 2026-10-10; Google's own pages couldn't be read from the cloud). Register as a developer who distributes outside Play in Google's Android developer console, with identity verification, the package name `io.github.zytocc.upnext` and the release certificate, before the APK is offered widely; check the steps and any fee there. Without it, people in those countries have to go through Android's slower "advanced flow" to install.

### On each release

Step 1 of "Releasing a version" sets `versionName`, `versionCode` and the F-Droid changelog. After the release, check the APK: `apksigner verify --print-certs upnext-android-X.Y.Z.apk` prints the release certificate's fingerprint, and it installs over the last version on a phone. F-Droid finds the tag itself once the app is in its repository (`contrib/fdroid/README.md` has the first submission).

To build it by hand, with JDK 17 or newer and the Android SDK (`ANDROID_HOME`): `cd android && ./gradlew :app:assembleRelease` makes an unsigned APK in `app/build/outputs/apk/release/`; with the four `UPNEXT_ANDROID_*` variables set as the workflow sets them (the keystore as a file path), it is signed.

## The Flatpak

`contrib/flatpak/` holds UpNext's Flatpak, `io.github.zytocc.UpNext`: the manifest, the launcher entry, the AppStream metadata, and the scripts that write the offline sources, build it and try it (`contrib/flatpak/README.md`). It builds from source with no network, on GNOME's runtime 51, the last with WebKitGTK for GTK 3.

The release workflow's `build-flatpak` job builds it from the tag with `contrib/flatpak/build.sh`, installs the bundle and runs it in its sandbox with `contrib/flatpak/smoke-test.sh`, and attaches `upnext-X.Y.Z-x86_64.flatpak` and its `.sha256`, only when the repository variable `UPNEXT_FLATPAK_BUNDLE` is `on`; otherwise the job is skipped, the host job leaves a notice, and the release goes out without it. It runs in Flathub's image for building GNOME apps (`ghcr.io/flathub-infra/flatpak-github-actions:gnome-51`, pinned by digest, as in the `flatpak` workflow) as a privileged container, which flatpak-builder needs for its own sandbox, so on GitHub's runners only. The `flatpak` workflow does the same with Flathub's linter on changes to `contrib/flatpak/` and the lock files, when the variable `UPNEXT_FLATPAK_CI` is `on`. Each is set once, as below; turn on `UPNEXT_FLATPAK_BUNDLE` only once the `flatpak` workflow has built green, and until then releases carry no bundle:

```sh
gh variable set UPNEXT_FLATPAK_CI --body on --repo zytocc/upnext
gh variable set UPNEXT_FLATPAK_BUNDLE --body on --repo zytocc/upnext
```

To move the image on (a new GNOME runtime, or a newer linter), take the new digest from `docker buildx imagetools inspect ghcr.io/flathub-infra/flatpak-github-actions:gnome-51` and replace it in both workflows. To move the source generators on, set `TOOLS_COMMIT` in `contrib/flatpak/generate-sources.sh` to a newer flatpak-builder-tools commit and run it.

**GNOME 52 drops WebKitGTK for GTK 3.** GNOME's runtime 52 (due in March 2027) carries only WebKitGTK for GTK 4, and Flathub stops updating runtime 51 about a year after its release, in the autumn of 2027. Before then the app window has to move to GTK 4 (wry 0.57.0, the newest on crates.io on 2026-10-10, still builds on GTK 3 and `webkit2gtk` 2.0.2), or the manifest has to build `webkit2gtk-4.1` itself as a module, which takes hours on Flathub's builders.

### Not on Flathub

UpNext isn't submitted to Flathub (the owner's decision, 2026-10-15): the release bundle is how the Flatpak is offered, and `docs/install/flatpak.md` says how to install and update it. ## The Microsoft Store package

`contrib/windows/msix/` holds the Microsoft Store package's manifest and pictures, and `contrib/windows/build-msix.ps1` packs the two programs with them, with the Windows SDK's MakePri and MakeAppx (`contrib/windows/README.md`). The package runs the same programs as the MSI, as an ordinary desktop app (`runFullTrust`). It adds the `upnext` and `upnext-app` aliases, so `upnext` works in a terminal, and a startup task, which is the Store copy's Start with Windows: the user turns it on in Windows Settings, Apps, Startup (`src/msix.rs` and `src/autostart.rs` say why). It keeps the library in `%LOCALAPPDATA%\upnext`, where every other copy keeps it, so it opens an existing library and uninstalling it keeps the library; that takes the restricted capability `unvirtualizedResources`, which the Store asks the publisher to justify. The Store signs what it publishes, so the package needs no certificate and no secret, and installing it from the Store brings no SmartScreen prompt. Once it's listed, `winget install` finds it in winget's `msstore` source.

The release workflow's `build-msix` job builds `upnext-x86_64-pc-windows-msvc.msix` and its `.sha256` from dist's Windows zip on a tag, once the repository variables `UPNEXT_MSIX_IDENTITY_NAME` and `UPNEXT_MSIX_PUBLISHER` are set (until then it's skipped and the host job leaves a notice), and uploads them as the run's `msix` artifact, not to the release: unsigned, the package installs only from the Store or as a development registration. Its version is the release's with a fourth number, 0, which the Store keeps for itself (`0.2.0.0`). Between releases, the `windows` workflow builds the same package from any commit when it's run by hand (Actions, windows, Run workflow), as its `upnext-msix-<commit>` artifact, with the unpacked folder for testing.

### Uploading a build by hand

The depots are made on Ubuntu 22.04, the system the release's programs are built on, so the Linux depot carries the libraries they were built against; elsewhere, in a container:

```sh
cd ~/src/upnext
docker run --rm -v "$PWD:/src" -w /src ubuntu:22.04 sh -c '
  apt-get update -qq && apt-get install -y -qq --no-install-recommends ca-certificates curl xz-utils python3 \
    libwebkit2gtk-4.1-0 libgtk-3-0 librsvg2-common glib-networking dconf-gsettings-backend libglib2.0-bin patchelf binutils &&
  contrib/steam/build-depots.sh --tag vX.Y.Z --out target/steam &&
  contrib/steam/fetch-sources.py --depot target/steam/linux --out target/steam-sources/upnext-steam-linux-sources.tar'
contrib/steam/smoke-test.sh target/steam/linux ubuntu:22.04     # optional: Docker and Xvfb
gh release upload vX.Y.Z target/steam-sources/upnext-steam-linux-sources.tar target/steam-sources/upnext-steam-linux-sources.tar.sha256 --repo zytocc/upnext
export STEAM_APP_ID=… STEAM_DEPOT_LINUX=… STEAM_DEPOT_WINDOWS=…   # from Steamworks
contrib/steam/upload.sh --depots target/steam --dry-run
STEAM_USERNAME=<builder> STEAMCMD=~/steamcmd/steamcmd.sh contrib/steam/upload.sh --depots target/steam
```

`build-depots.sh` fetches the tag's Linux archive and Windows zip from the release, checks them against their `.sha256` files, and lays out `target/steam/linux` and `target/steam/windows`. `fetch-sources.py` gathers the Ubuntu source packages of exactly the libraries and versions the Linux depot carries into one tar (`contrib/steam/README.md`, "The libraries' source"), which goes on the release before any build reaches Steam: most of those libraries are under the LGPL or the GPL, and the depot's `share/licenses/PACKAGES.txt` tells its readers to find their source there, under that name. `upload.sh` fills in `contrib/steam/build/` with the ids and runs steamcmd, which uploads both depots as one build and sets it live on `beta` (`--branch` names another beta branch; never the default one, which is set live by hand in Steamworks after checking). Run it on Linux, so the Linux depot keeps its executable bits.

### Uploading from the release workflow (once the manual route has worked)

The release workflow's `build-steam-depots` job makes the depots on every tag once the repository variable `UPNEXT_STEAM_DEPOTS` is `on`, runs the smoke test on the Linux one, and keeps them as the run's `steam-depots` artifact (a tar, so the executable bits survive), with the Linux depot's library sources as the `steam-sources` artifact. Once the release is published, its `attach-steam-sources` job attaches `upnext-steam-linux-sources.tar` and its `.sha256` to it, whether or not the upload to Steam is on. Its `publish-steam` job waits for that, then uploads the depots to `beta` after the release is published, once `UPNEXT_STEAM_UPLOAD` is `on` and the builder account and ids are set; without them it says what's missing in a notice and the release stands. Neither has run yet, since no version has been tagged.

```sh
gh variable set UPNEXT_STEAM_DEPOTS --body on --repo zytocc/upnext
gh variable set STEAM_APP_ID --body <app id> --repo zytocc/upnext
gh variable set STEAM_DEPOT_LINUX --body <Linux depot id> --repo zytocc/upnext
gh variable set STEAM_DEPOT_WINDOWS --body <Windows depot id> --repo zytocc/upnext
# steamcmd's bootstrap, which the job checks before running it (it updates itself after):
curl -fsSLO https://steamcdn-a.akamaihd.net/client/installer/steamcmd_linux.tar.gz && sha256sum steamcmd_linux.tar.gz
gh variable set STEAMCMD_SHA256 --body <that hash> --repo zytocc/upnext
gh secret set STEAM_USERNAME --repo zytocc/upnext                 # the builder account's name
base64 -w0 ~/steamcmd/config/config.vdf | gh secret set STEAM_CONFIG_VDF --repo zytocc/upnext
gh variable set UPNEXT_STEAM_UPLOAD --body on --repo zytocc/upnext
```

`STEAM_BRANCH` names a branch other than `beta`. Steam asks for Steam Guard again from time to time; when `publish-steam` fails asking for a code, sign the builder in again with steamcmd and set `STEAM_CONFIG_VDF` from the new file. When Valve replaces steamcmd's bootstrap, the job's checksum fails: download it, check it's Valve's, and set `STEAMCMD_SHA256` again.

### On each release

Check that the release has `upnext-steam-linux-sources.tar` and its `.sha256` (the `attach-steam-sources` job); `publish-steam` doesn't run without them. The run's `publish-steam` log ends with the upload (or its notice). Install the build from `beta` on a Deck and on Windows, start both launch options, make a pick and press Play, then set it live on the default branch in Steamworks.

## Building the shared game data

The shared game data (People say, Vibes and review tags for the 10,000 most-owned games on Steam, CC0) is built on a Linux machine with a checkout and published on UpNext's data server, `https://data.upnext.games`, as two files: `upnext-seed-<date>.jsonl.gz` and `upnext-seed.json`. The app's default address (`DEFAULT_URL` in `src/seed.rs`) is that manifest's, so new data reaches every install whenever it's published, with or without a release of the app. The server is a public Cloudflare R2 bucket behind that address, with no Worker; [UpNext's data server](#upnexts-data-server-once) sets it up. The build runs in a database of its own, never the live one, and its titles come from SteamSpy's catalogue, not from anyone's library: `upnext seed build` refuses UpNext's usual database and any database with a library in it. Every step stores as it goes, so a step that stops (a failure, a reboot, a timeout) carries on when the same command runs again.

The steps, in order. The examples use `~/src/upnext` for the checkout, `~/upnext-seed` for the build's folder and `http://192.168.0.42:8000/v1` for the model server; use your own.

1. **The binary.** No UI is needed:

   ```sh
   cd ~/src/upnext && git pull && cargo build --release --no-default-features
   U=~/src/upnext/target/release/upnext
   loginctl enable-linger "$USER"   # once: user units keep running after you log out
   ```

2. **The fetch, any time** (it doesn't use the model). `seed build` reads SteamSpy's catalogue (one page a minute, 13 pages) and asks the Steam store what each app is, until the list holds 10,000 games: about five hours. `seed fetch` then fetches their reviews, about nine hours, and their GOG ids: from Wikidata, and for the games Wikidata gives only a GOG store page, from GOG's catalogue by the page's slug (one search a page, about 15 minutes). As a user unit, so it survives logging out:

   ```sh
   systemd-run --user --unit=upnext-seed-fetch --setenv=UPNEXT_DATA_DIR=$HOME/upnext-seed -p KillSignal=SIGINT \
     /bin/sh -c "$U seed build && $U seed fetch"
   journalctl --user -u upnext-seed-fetch -f          # what it's doing
   UPNEXT_DATA_DIR=~/upnext-seed $U seed status       # where the build stands
   ```

   If it stops early (`seed fetch` says some requests failed, or the Steam store rate-limits), run the same `systemd-run` command again once it has ended (a transient unit is gone when it finishes, so `systemctl --user start` can't restart it), or run the two commands in a terminal. Both pick up where the last run stopped.

3. **The model, once.** The build's own settings, in its own database:

   ```sh
   export UPNEXT_DATA_DIR=~/upnext-seed
   $U config set llm_backend openai
   $U config set openai_base_url http://192.168.0.42:8000/v1
   $U config set openai_model qwen3.8-27b
   $U config set openai_thinking off
   ```

4. **The summaries, from 1 am,** set up once the fetch has finished (a build runs one step at a time). About six hours for 10,000 titles at three calls at a time. This timer starts `seed generate` at 1 am every night and stops it after seven hours, so it never runs into the day; a night that doesn't finish is carried on the next night, and a night with nothing left to write makes no AI call. `KillSignal=SIGINT` stops it as Ctrl-C does, so the job is recorded as stopped.

   ```sh
   systemd-run --user --unit=upnext-seed-generate --on-calendar='*-*-* 01:00:00' \
     --setenv=UPNEXT_DATA_DIR=$HOME/upnext-seed -p RuntimeMaxSec=7h -p KillSignal=SIGINT \
     $U seed generate
   systemctl --user list-timers upnext-seed-generate.timer   # when it runs next
   journalctl --user -u upnext-seed-generate                 # what it did
   ```

   To start right away instead (when the model machine is free): `systemctl --user start upnext-seed-generate.service`. Without systemd, `echo "UPNEXT_DATA_DIR=$HOME/upnext-seed $U seed generate" | at 01:00` runs it once. It writes with the settings of step 3 and says which at the start: "Writing summaries with qwen3.8-27b at http://192.168.0.42:8000/v1, thinking off". After the summaries pass, a second one picks up titles a reply left out, and summaries that copied a run of 8 or more words from a review are written once more, in the model's own words.

5. **The export**, once `seed status` shows a summary for every game with reviews (or `seed generate` stops saying some have none):

   ```sh
   systemctl --user stop upnext-seed-generate.timer
   UPNEXT_DATA_DIR=~/upnext-seed $U seed export --out ~/upnext-seed/release
   ```

   It writes `upnext-seed-<today>.jsonl.gz` and `upnext-seed.json`, and leaves out games without a summary and summaries that still copy a review. Check them on a mock library, which needs no AI: `UPNEXT_DATA_DIR=$(mktemp -d) sh -c "$U mock-library && $U seed apply ~/upnext-seed/release/upnext-seed.json"`.

6. **Publishing** is the maintainer's call, after Valve's API terms are read. With wrangler from the verdicts service's folder, signed in to the account that holds the bucket (`npx wrangler whoami`), upload the data file first and the manifest after it, so the manifest never names a file that isn't there yet. `<date>` is the date in the data file's name, which the manifest's `file` gives:

   ```sh
   cd ~/src/upnext/services/verdicts && npm ci
   npx wrangler r2 object put upnext-shared-data/upnext-seed-<date>.jsonl.gz --remote \
     --file ~/upnext-seed/release/upnext-seed-<date>.jsonl.gz \
     --content-type application/gzip --cache-control "public, max-age=31536000, immutable"
   npx wrangler r2 object put upnext-shared-data/upnext-seed.json --remote \
     --file ~/upnext-seed/release/upnext-seed.json \
     --content-type application/json --cache-control "public, max-age=300"
   curl -sSI https://data.upnext.games/upnext-seed.json | grep -i '^content-type'   # application/json
   UPNEXT_DATA_DIR=$(mktemp -d) sh -c "$U mock-library && $U seed apply https://data.upnext.games/upnext-seed.json"
   ```

   Without `--remote`, wrangler writes to a local bucket under `.wrangler/` and nothing is published. A dated data file never changes, so it may be cached for a year; the manifest changes with each publish, so caches keep it five minutes. Leave the content encoding unset: UpNext unpacks the `.gz` itself. Older data files can stay in the bucket (about 3 MB each): only the manifest says which is newest, and installs apply their own kept copy. Nothing else from the build's folder goes anywhere: not its database, not its settings.

### UpNext's data server (once)

A bucket of its own, separate from the verdicts service's private one, served as plain files at `https://data.upnext.games`. R2's free tier covers it (10 GB of storage, 10 million reads a month, no egress charge; [VERDICTS-SERVICE.md](VERDICTS-SERVICE.md) has the table). The steps use the Cloudflare dashboard; each has its wrangler line, run from `services/verdicts` after `npm ci` and `npx wrangler login`. No step puts an account id or zone id in the repository.

1. **R2.** If the verdicts service runs on the same account, R2 is on already. Otherwise turn it on once: Storage & Databases › R2 Object Storage, which asks for a payment method even on the free plan.
2. **The bucket.** R2 Object Storage › Create bucket. Name it `upnext-shared-data`, leave the location on Automatic and the storage class on Standard, and select Create bucket.

   ```sh
   npx wrangler r2 bucket create upnext-shared-data
   ```

3. **Its address.** In the bucket, Settings › Custom Domains › Add. Enter `data.upnext.games` (the domain has to be a zone in the same Cloudflare account), select Continue, then Connect Domain. Cloudflare adds the DNS record itself, and the domain shows Active once its certificate is issued, usually within a few minutes. The bucket's files are then readable by anyone at that address, which is what makes it public.

   ```sh
   npx wrangler r2 bucket domain add upnext-shared-data --domain data.upnext.games --zone-id <zone id>
   npx wrangler r2 bucket domain list upnext-shared-data   # data.upnext.games, enabled
   ```

   The zone id is on the domain's Overview page in the dashboard (API, Zone ID). Leave the bucket's Public Development URL (`r2.dev`) disabled: it is rate-limited and not meant for downloads, and the custom domain is the only address the app knows.
4. **Check it** once the first data is uploaded (step 6 above): `curl -sSI https://data.upnext.games/upnext-seed.json` answers `200` with `content-type: application/json`. Until then the app's wizard and Settings say no shared data is published yet, which isn't an error.

A copy of UpNext run by someone else can publish its own data the same way under its own domain; players then give that manifest's address in Settings › Library data or to `upnext seed apply`.

## Going public (once, for 0.1.0)

The public repository starts from one squashed commit, authored and committed with the owner's GitHub noreply address in UTC, under `zytocc`, with the v0.1.0 tag on that commit, or on the fix after it that a prerelease needed (step 6). Only the owner runs the GitHub steps, from a terminal with `gh` signed in as an admin of `zytocc`, and only when nothing else is pushing to `main`. The squashed tree leaves out the private repository's planning and session notes, which stay in the archive with the rest of the old history.

The squash alone doesn't take the old history out of this repository: the pull requests Dependabot opened keep their refs (`refs/pull/N/head`), which a public repository serves to anyone and only GitHub Support can delete, and the old Actions runs and their logs become public too. So the public repository is a new one under the same name, and this one is renamed and stays private as the archive (the owner's decision, 2026-10-04). Route B below is the alternative.

The archive keeps the self-hosted runners and `UPNEXT_RUNNER_*` variables until they're removed: delete the variables and remove both runners, with their services, as `docs/dev/CI-RUNNERS.md` says ("Flipping back to GitHub's runners", "Removing a runner"). Do it before archiving, which makes the repository read-only.

Every existing clone has the old history, which shares nothing with the new `main`: clone again, or in a clone with no work of its own, `git fetch origin && git checkout -B main origin/main`. Development sessions start again from the new `main`.

Then set up the package repository ([The package repository](#the-package-repository)): Cloudsmith's free plan is for public repositories, and the v0.1.0 packages can be pushed by re-running that run's `publish-cloudsmith` job once the secret and variable are set.

### Route B: keep this repository

If the old history should stay in this repository instead: push the squashed commit over `main` (`git push --force origin public:main`), close the open pull requests and delete their branches, delete the old workflow runs (`gh run list --limit 1000 --json databaseId --jq '.[].databaseId' | xargs -I{} gh api -X DELETE repos/zytocc/upnext/actions/runs/{}`), and ask GitHub Support to remove the pull request refs and cached views of the old commits (their "Removing sensitive data" guide). Delete the `UPNEXT_RUNNER_*` variables and remove the self-hosted runners too (`docs/dev/CI-RUNNERS.md`, "Flipping back to GitHub's runners"). Only once they confirm, go on with steps 4 to 7.
