# Releases

A release is a `v*` tag on `main`. The tag starts two workflows: `docker` pushes the image as the version and `latest`, and `release` (`.github/workflows/release.yml`, generated by [dist](https://github.com/axodotdev/cargo-dist) with the hand edits its header lists) builds the files below and publishes the GitHub release with the tag's CHANGELOG section as its notes. Every package has a `.sha256`.

| Files | Built by | Notes |
|---|---|---|
| Linux archives, x86_64 and aarch64 (`upnext-<target>.tar.xz`) | dist (the second natively on `ubuntu-22.04-arm`) | `upnext`, `upnext-app` with the web UI inside, README, CHANGELOG, both licences, `THIRD_PARTY_NOTICES.txt`, `upnext.service`, `upnext.desktop`, `icons/hicolor/`. Built on Ubuntu 22.04: glibc 2.35 or newer, WebKitGTK 4.1 and GTK 3 at run time. |
| Windows zip (`upnext-x86_64-pc-windows-msvc.zip`) | dist, Windows Server 2022, MSVC | `upnext.exe`, `upnext-app.exe` and the archives' other files. |
| MSI | `build-msi`: `contrib/windows/build-msi.ps1`, WiX 3.14.1 | Per-user. Not signed until SignPath Foundation accepts the project ([Code signing policy](../../README.md#code-signing-policy)); then the two exes and the MSI go through SignPath. |
| `.deb` and `.rpm`, amd64 and arm64 | `build-linux-packages`: `contrib/linux/build-packages.sh`, [nfpm](https://nfpm.goreleaser.com) 2.47.0 | `contrib/linux/smoke-test.sh` installs the amd64 packages in `debian:12`, `ubuntu:24.04` and `fedora:44`; a failure stops the release. |
| `upnext-bin-<pkgver>-1-x86_64.pkg.tar.zst` and `PKGBUILD` | `build-arch-package`: `contrib/arch/build-package.sh`, `render-pkgbuild.sh` | Built by makepkg in `archlinux:base-devel` from the very `PKGBUILD` the release publishes; any namcap error stops the release; smoke-tested in `archlinux:latest`. `v0.2.0-rc.1` becomes `0.2.0rc.1`. No secrets. |
| Signed pacman repository | `sign-pacman-repo` | When the signing key is set up ([The Arch package repository](#the-arch-package-repository)). |
| `.apk`, `.flatpak` | `build-apk`, `build-flatpak` | When set up ([The Android app](#the-android-app), [The Flatpak](#the-flatpak)). |
| apt and dnf packages on Cloudsmith | `publish-cloudsmith` | When set up ([The package repository](#the-package-repository)); skips prereleases. |

The Microsoft Store package and the Steam depots are run artifacts, not release files.

## Variables and secrets

A feature that is off leaves a notice in the run, not a failure. Arch signing is different: with its variable set and no secret, the release fails.

| Feature | Job | Turned on by | Set up in |
|---|---|---|---|
| Arch repository | `sign-pacman-repo` | variable `PACMAN_KEY_FINGERPRINT`; secrets `PACMAN_SIGNING_KEY`, and `PACMAN_SIGNING_KEY_PASSPHRASE` if the subkey has one | [The Arch package repository](#the-arch-package-repository) |
| Android app | `build-apk` | secrets `UPNEXT_ANDROID_KEYSTORE`, `UPNEXT_ANDROID_KEYSTORE_PASSWORD`, `UPNEXT_ANDROID_KEY_ALIAS`, `UPNEXT_ANDROID_KEY_PASSWORD` | [The Android app](#the-android-app) |
| Flatpak bundle | `build-flatpak` | variable `UPNEXT_FLATPAK_BUNDLE` = `on` (`UPNEXT_FLATPAK_CI` = `on` for the `flatpak` workflow) | [The Flatpak](#the-flatpak) |
| Microsoft Store package | `build-msix` | variables `UPNEXT_MSIX_IDENTITY_NAME` and `UPNEXT_MSIX_PUBLISHER` (also `UPNEXT_MSIX_PUBLISHER_DISPLAY_NAME`, and `UPNEXT_MSIX_DISPLAY_NAME` if the reserved name isn't "UpNext") | [The Microsoft Store package](#the-microsoft-store-package) |
| Steam depots, upload | `build-steam-depots`, `attach-steam-sources`, `publish-steam` | variables `UPNEXT_STEAM_DEPOTS` and `UPNEXT_STEAM_UPLOAD` = `on`, plus the ids, `STEAMCMD_SHA256` and two secrets | [`contrib/steam/README.md`](../../contrib/steam/README.md#setting-up-the-workflow) |
| Cloudsmith | `publish-cloudsmith` | variable `CLOUDSMITH_REPOSITORY`; secret `CLOUDSMITH_API_KEY` (without it the job stops with a notice) | [The package repository](#the-package-repository) |
| Self-hosted runners | `ci`, `windows`, `docker` | variables `UPNEXT_RUNNER_*` | [CI-RUNNERS.md](CI-RUNNERS.md) |

## Releasing a version

1. On an up-to-date `main` with CI green, set `version` in `Cargo.toml`. Run `cargo check` to update `Cargo.lock` and `UPNEXT_UPDATE_OPENAPI=1 cargo test --locked openapi` to update `docs/openapi.json`, which carries the version too. In `android/app/build.gradle.kts` set `versionName` to the same version and `versionCode` to major × 1,000,000 + minor × 1,000 + patch (`cd android && ./gradlew :app:checkVersion` checks both). Add `android/fastlane/metadata/android/en-US/changelogs/<versionCode>.txt` with a line or two for F-Droid.
2. In `CHANGELOG.md`, turn `## [Unreleased]` into `## [X.Y.Z] - YYYY-MM-DD` with that day's date and start a new empty `## [Unreleased]` above it. In `contrib/flatpak/io.github.zytocc.UpNext.metainfo.xml`, add `<release version="X.Y.Z" date="YYYY-MM-DD">` with a line on what's new at the top of `<releases>`, and run `appstreamcli validate --no-net` on that file.
3. Preview and try the build:
   - `dist plan --tag=vX.Y.Z` lists the files. `dist build --tag=vX.Y.Z` builds the archive for the machine it runs on into `target/distrib/` (build `web/dist` first: `cd web && npm ci && npm run build`).
   - MSI: build it on Windows and go through "Checking an MSI" in `contrib/windows/README.md`.
   - Linux packages: `cargo build --release --locked --bins`, then `contrib/linux/build-packages.sh --bin-dir target/release` (writes `target/linux-packages`), then `contrib/linux/smoke-test.sh` on each, as the workflow does (its comment has the command; needs docker).
   - Arch package: after `dist build`, `contrib/arch/build-package.sh --tag vX.Y.Z --dist-dir target/distrib` writes the package and `PKGBUILD` to `target/arch-package`; then run the smoke test in `archlinux:latest`. It needs docker and Arch's mirrors; on Arch itself `--host` uses the machine's makepkg (the script's comment has the options).
4. Commit, push, and wait for `ci` to pass on that commit. Check that the `notices` workflow's latest run on `main` passed too (run it from the Actions tab if unsure): the container image relies on it ([Third-party notices](#third-party-notices)).
5. Tag and push. Use the GitHub noreply address and `TZ=UTC`; the tag is public:

   ```sh
   git config user.email                        # the noreply address
   TZ=UTC git tag -a vX.Y.Z -m "UpNext X.Y.Z"
   git for-each-ref refs/tags/vX.Y.Z --format='%(taggername) %(taggeremail) %(taggerdate:iso)'
   git push origin vX.Y.Z
   gh run watch "$(gh run list --workflow release.yml --limit 1 --json databaseId --jq '.[0].databaseId')"
   ```

6. Check the release page against this list, then follow [Checking a release](#checking-a-release):

   - [ ] Always: the two Linux archives, the Windows zip, the MSI, the four Debian and Fedora packages and the Arch package, each with its `.sha256`; `PKGBUILD`; the source archive; `sha256.sum` (dist's files only).
   - [ ] Arch signing on: the Arch package's `.sig`, `upnext.db`, `upnext.files`, their two `.sig` files and `upnext-signing-key.asc`.
   - [ ] Android key set: `upnext-android-X.Y.Z.apk` and its `.sha256`.
   - [ ] `UPNEXT_FLATPAK_BUNDLE` on: `upnext-X.Y.Z-x86_64.flatpak` and its `.sha256`.
   - [ ] Steam on: `upnext-steam-linux-sources.tar` and its `.sha256`; the depots are the run's `steam-depots` artifact.
   - [ ] Microsoft Store variables set: the run's `msix` artifact ([Microsoft Store](#microsoft-store) says what to do with it).
   - [ ] Cloudsmith on, stable release: the `publish-cloudsmith` log names each package's page.

7. Before announcing, submit the Windows files to Microsoft so Defender's machine-learning detections (names ending `!ml`, such as `Wacatac!ml`) don't flag them. Do it for every release. At [Microsoft's file submission page](https://www.microsoft.com/en-us/wdsi/filesubmission), sign in, choose "Software developer", and submit the MSI, then `upnext.exe` and `upnext-app.exe` from the zip, one submission each, for Microsoft Defender Antivirus. Say the file is clean (or incorrectly detected, if Defender already flags it), and give the release page's link and the file's SHA-256.
8. Open the pull request that brings the release to winget ([winget](#winget)). `site/install.sh` needs nothing: it installs whichever release is newest.

### Prereleases

A tag like `v0.2.0-rc.1` makes a prerelease. dist releases only a crate whose version is the tag's, so step 1 sets the version to `0.2.0-rc.1` for that tag (`versionCode` is 0.2.0's) and a commit of its own sets it back to `0.2.0` before the final tag. The notes are the `## [0.2.0]` section, so step 2 is done once, for the first candidate. The MSI's version drops the suffix (0.2.0).

### Changing dist's settings

Edit `dist-workspace.toml` (or `.github/build-setup.yml`, the steps that build the web UI first), then regenerate the workflow and commit it with them. `allow-dirty = ["ci"]` in that file stops `dist generate` from rewriting `release.yml`: comment it out, run `dist generate`, put it back, and keep the hand edits the header of `release.yml` lists. `dist init` upgrades dist itself.

## Checking a release

On a machine that has never built UpNext and has no Rust or Node:

```sh
V=X.Y.Z
curl -LO "https://github.com/zytocc/upnext/releases/download/v$V/upnext-x86_64-unknown-linux-gnu.tar.xz"
curl -LO "https://github.com/zytocc/upnext/releases/download/v$V/upnext-x86_64-unknown-linux-gnu.tar.xz.sha256"
sha256sum -c upnext-x86_64-unknown-linux-gnu.tar.xz.sha256
tar xf upnext-x86_64-unknown-linux-gnu.tar.xz
```

The folder has `THIRD_PARTY_NOTICES.txt` beside the licences. Then follow [Release archive](../install/linux.md#release-archive) as written: install the two libraries, put the binaries on the `PATH`, run `upnext --version` (it must print the version), `upnext doctor` and `upnext serve`, and open `http://127.0.0.1:8787`. The setup page must load (the embedded UI, not the "this build has no web UI" placeholder), and Settings › About's "third-party notices" link must open the notices. `upnext app` opens the window. Point `UPNEXT_DATA_DIR` at an empty folder if the machine already has an UpNext database.

On a Windows 11 machine, in PowerShell:

```powershell
$V = "X.Y.Z"
$base = "https://github.com/zytocc/upnext/releases/download/v$V"
Invoke-WebRequest -OutFile upnext-x86_64-pc-windows-msvc.msi "$base/upnext-x86_64-pc-windows-msvc.msi"
Invoke-WebRequest -OutFile upnext-x86_64-pc-windows-msvc.msi.sha256 "$base/upnext-x86_64-pc-windows-msvc.msi.sha256"
(Get-FileHash upnext-x86_64-pc-windows-msvc.msi).Hash.ToLower()   # the same as the first word of:
Get-Content upnext-x86_64-pc-windows-msvc.msi.sha256
```

Install it and go through "Checking an MSI" in `contrib/windows/README.md` from step 1. Also download it once in a browser, which marks the file as from the internet and brings up SmartScreen, and check that [Windows](../install/windows.md#smartscreen-and-checksums) describes what happens.

For the Linux packages, use a Debian, Ubuntu or Fedora desktop, or [distrobox](https://distrobox.it) boxes of `debian:13`, `ubuntu:24.04` and `fedora:44` on another distribution (they share the display and the home folder, so set `UPNEXT_DATA_DIR` to an empty folder there):

```sh
V=X.Y.Z
base="https://github.com/zytocc/upnext/releases/download/v$V"
# Debian and Ubuntu (arm64: _arm64.deb)
curl -LO "$base/upnext_$V-1_amd64.deb" -LO "$base/upnext_$V-1_amd64.deb.sha256"
sha256sum -c "upnext_$V-1_amd64.deb.sha256" && sudo apt install "./upnext_$V-1_amd64.deb"
# Fedora (arm64: .aarch64.rpm)
curl -LO "$base/upnext-$V-1.x86_64.rpm" -LO "$base/upnext-$V-1.x86_64.rpm.sha256"
sha256sum -c "upnext-$V-1.x86_64.rpm.sha256" && sudo dnf install "./upnext-$V-1.x86_64.rpm"

upnext --version          # X.Y.Z
upnext doctor
upnext app                # the window
sudo apt remove upnext    # or: sudo dnf remove upnext; the data folder stays
```

On a desktop (not a box), UpNext is in the launcher under Games with its icon, and `systemctl --user enable --now upnext` starts the service.

For the Arch package, use an Arch desktop (or a distrobox box of `archlinux:latest`, with `UPNEXT_DATA_DIR` set to an empty folder), both ways [Arch Linux](../install/linux.md#arch-linux) gives:

```sh
V=X.Y.Z
base="https://github.com/zytocc/upnext/releases/download/v$V"
mkdir upnext-bin && cd upnext-bin
curl -fsSLO "$base/PKGBUILD"
makepkg -si                       # downloads the archive, checks it, installs upnext-bin
upnext --version                  # X.Y.Z
upnext doctor
upnext app                        # the window
sudo pacman -R upnext-bin         # the data folder stays
curl -fsSLO "$base/upnext-bin-$V-1-x86_64.pkg.tar.zst" -LO "$base/upnext-bin-$V-1-x86_64.pkg.tar.zst.sha256"
sha256sum -c "upnext-bin-$V-1-x86_64.pkg.tar.zst.sha256" && sudo pacman -U "./upnext-bin-$V-1-x86_64.pkg.tar.zst"
```

For a prerelease the file name has the version without its hyphen (`0.2.0rc.1`). On a desktop, UpNext is in the launcher under Games with its icon, a Steam game launches from it, and `systemctl --user enable --now upnext` starts the service. On a machine that had a `cargo install` copy, the steps replace it without touching the library.

## Third-party notices

`THIRD_PARTY_NOTICES.txt` at the repository's root lists everything built into UpNext (Rust crates, npm packages, the game data credits, Microsoft's WebView2 loader and tini) with each licence text. `android/app/src/main/assets/third_party_notices.txt` does the same for the Android app. `contrib/notices/generate.mjs` writes both and they are committed; [Checks](../contributing/checks.md#third-party-notices) has the commands to regenerate them.

- The `notices` workflow (`.github/workflows/notices.yml`) fails when the committed files differ from a fresh run. A Dependabot update of a crate or npm package fails it until someone regenerates on the branch and pushes.
- The release's `check-notices` job runs the same check on the tag, and the host job doesn't publish a release whose notices differ. The `docker` workflow doesn't wait for it, so step 4 of [Releasing a version](#releasing-a-version) checks the `notices` workflow instead.
- Every artefact carries the file beside `LICENSE-MIT` and `LICENSE-APACHE`, and every build serves it at `/third-party-notices.txt` (Settings › About links to it). The build scripts and smoke tests check this, except for the archives and the zip, which [Checking a release](#checking-a-release) covers, and the APK, which nothing checks.

When a pinned entry changes (a new `webview2-com-sys`, tini or zxing-android-embedded), the script stops and says what to look at. For the WebView2 loader:

1. Download the `Microsoft.Web.WebView2` package whose version is the new DLL's file version, from `api.nuget.org/v3-flatcontainer/microsoft.web.webview2/`.
2. Check that its `build/native/x64/WebView2LoaderStatic.lib` has the crate's SHA-256.
3. Replace the version, the hash and the two files in `contrib/notices/webview2/`.

tini's licence is in `contrib/notices/tini/`, checked against the version the `Dockerfile` downloads. Raise cargo-about's version only together with a regeneration, since it words some standard texts.

## Platform steps for each release

### Android

Step 1 of [Releasing a version](#releasing-a-version) sets `versionName`, `versionCode` and the F-Droid changelog. After the release, run `apksigner verify --print-certs upnext-android-X.Y.Z.apk`: it prints the release certificate's fingerprint. Install the APK over the last version on a phone. F-Droid finds the tag itself once the app is in its repository (`contrib/fdroid/README.md`).

### Microsoft Store

Download the run's `msix` artifact (`gh run download <run id> --name msix --repo zytocc/upnext`), check the package against its `.sha256`, and upload it in a new submission's Packages page, replacing the last one. Each submission's version must be higher than the last. Certification takes hours to a few days; Partner Center emails the result.

### winget

`winget install Zytoc.UpNext` installs the release's MSI. The package files live in [microsoft/winget-pkgs](https://github.com/microsoft/winget-pkgs); each release reaches it by a pull request from the maintainer's fork, which a Microsoft moderator merges after its checks pass. Once the release page has the MSI and the CHANGELOG section is dated, run the commands under "The pull request" in `contrib/winget/README.md` with the new version. If the pull request is labelled `Needs-Author-Feedback`, its comments say what to change.

### Steam

Check that the release has `upnext-steam-linux-sources.tar` and its `.sha256` (`publish-steam` doesn't run without them) and that the `publish-steam` log ends with the upload. Install the build from `beta` on a Deck and on Windows, start both launch options, make a pick and press Play, then set the build live on the default branch in Steamworks.

### Arch repository

After a stable release, on an Arch machine with the repository set up, `sudo pacman -Syu` must offer the new `upnext-bin`, and `pacman -Qi upnext-bin` must say "Validated By: Signature" once it's installed. A prerelease carries the same files, reached through a `Server` line naming its tag.

### Cloudsmith

`publish-cloudsmith` pushes the four packages after the GitHub release is published. Check one install from the repository, as in [Checking a release](#checking-a-release). Cloudsmith indexes and signs each package after the push, and one that fails there shows the reason on its page. It refuses a package whose name and version it already has, so after a partial push, delete the ones that made it in the web app first, or upload the rest there.

## The Android app

The `build-apk` job builds the app from `android/` on each tag, signs it with the release key and attaches `upnext-android-X.Y.Z.apk` and its `.sha256`. Every APK must carry the same key, so each installs over the last, and F-Droid ships the same signature (`contrib/fdroid/`). A lost key means a new package name and every install made again.

### Making the release key (once)

On a computer you trust, with a JDK (`keytool`):

```sh
keytool -genkeypair -v -keystore upnext-release.jks -alias upnext -keyalg RSA -keysize 4096 -validity 10000 \
  -dname "CN=UpNext contributors"
keytool -list -v -keystore upnext-release.jks -alias upnext   # note the SHA-256 fingerprint
```

Keep `upnext-release.jks` and its passwords offline, with a backup somewhere else. Then set the four repository secrets, used on tags only:

```sh
R=zytocc/upnext
base64 -w0 upnext-release.jks | gh secret set UPNEXT_ANDROID_KEYSTORE --repo $R
gh secret set UPNEXT_ANDROID_KEYSTORE_PASSWORD --repo $R
gh secret set UPNEXT_ANDROID_KEY_ALIAS --repo $R --body upnext
gh secret set UPNEXT_ANDROID_KEY_PASSWORD --repo $R
```

Put the fingerprint (lowercase, without colons) in `AllowedAPKSigningKeys` in `contrib/fdroid/io.github.zytocc.upnext.yml`, and later in Google Play's App Signing as the app's own key, so all three carry one signature.

### Google's developer verification (once)

Google asks developers who distribute outside Play to register in the Android developer console. Register with identity verification, the package name `io.github.zytocc.upnext` and the release certificate before the APK is offered widely, and check the current rules and any fee in the console.

### Building by hand

With JDK 17 or newer and the Android SDK (`ANDROID_HOME`), `cd android && ./gradlew :app:assembleRelease` makes an unsigned APK in `app/build/outputs/apk/release/`. With the four `UPNEXT_ANDROID_*` variables set as the workflow sets them (the keystore as a file path), it is signed.

## The Flatpak

`contrib/flatpak/` holds the Flatpak `io.github.zytocc.UpNext`: the manifest, launcher entry, AppStream metadata and the scripts that write the offline sources, build it and try it (`contrib/flatpak/README.md`). It builds from source with no network, on GNOME's runtime 51.

The `build-flatpak` job builds it from the tag with `contrib/flatpak/build.sh`, runs it in its sandbox with `contrib/flatpak/smoke-test.sh`, and attaches `upnext-X.Y.Z-x86_64.flatpak` and its `.sha256`. It runs in Flathub's image for building GNOME apps (`ghcr.io/flathub-infra/flatpak-github-actions:gnome-51`, pinned by digest) as a privileged container, so on GitHub's runners only. The `flatpak` workflow builds it with Flathub's linter on changes to `contrib/flatpak/` and the lock files. Turn each on once; turn on `UPNEXT_FLATPAK_BUNDLE` only after the `flatpak` workflow has built green:

```sh
gh variable set UPNEXT_FLATPAK_CI --body on --repo zytocc/upnext
gh variable set UPNEXT_FLATPAK_BUNDLE --body on --repo zytocc/upnext
```

To move the image on, take the new digest from `docker buildx imagetools inspect ghcr.io/flathub-infra/flatpak-github-actions:gnome-51` and replace it in both workflows. To move the source generators on, set `TOOLS_COMMIT` in `contrib/flatpak/generate-sources.sh` to a newer flatpak-builder-tools commit and run it.

The release bundle is how the Flatpak is offered (`docs/install/flatpak.md`). The runtime and SDK extensions come from Flathub, and the `flatpak` workflow runs Flathub's linter, with the expected findings in `contrib/flatpak/lint-exceptions.json`.

The metadata names the screenshots `docs/images/pick.png` and `docs/images/big-screen.png`, which must be on `main` first. Take the big-screen one with `UPNEXT_README_SHOT=1 npm run e2e -- readme-shot` in `web/`, on a machine that reaches Steam's image servers.

## The Microsoft Store package

`contrib/windows/msix/` holds the Store package's manifest and pictures, and `contrib/windows/build-msix.ps1` packs the two programs with them (`contrib/windows/README.md`). It runs the same programs as the MSI, as a desktop app (`runFullTrust`), adds the `upnext` and `upnext-app` aliases and a startup task (the user turns it on in Windows Settings, Apps, Startup), and keeps the library in `%LOCALAPPDATA%\upnext` like every other copy, which needs the restricted capability `unvirtualizedResources`. The Store signs what it publishes, so the package needs no certificate and no secret.

The `build-msix` job builds `upnext-x86_64-pc-windows-msvc.msix` and its `.sha256` from dist's Windows zip on a tag, once the two variables below are set, and uploads them as the run's `msix` artifact. The version is the release's with a fourth number, 0 (`0.2.0.0`). Between releases, running the `windows` workflow by hand (Actions, windows, Run workflow) builds the same package from any commit as its `upnext-msix-<commit>` artifact.

### Partner Center (once)

1. Register as an individual developer at [storedeveloper.microsoft.com](https://storedeveloper.microsoft.com), "Get started for free", with a Microsoft account. It asks for a government ID and a selfie. Once registered, [aka.ms/submitwindowsapp](https://aka.ms/submitwindowsapp) opens Partner Center.
2. Apps and games, New product, "MSIX or PWA app", and reserve the app's name.
3. In the new app, Product management, Product identity lists `Package/Identity/Name`, `Package/Identity/Publisher` and `Package/Properties/PublisherDisplayName`. Put them in repository variables. The Store takes the package only when it matches Partner Center's, so set all three. Set `UPNEXT_MSIX_DISPLAY_NAME` too if the reserved name isn't "UpNext":

   ```sh
   gh variable set UPNEXT_MSIX_IDENTITY_NAME --body 'Package/Identity/Name' --repo zytocc/upnext
   gh variable set UPNEXT_MSIX_PUBLISHER --body 'Package/Identity/Publisher, CN=...' --repo zytocc/upnext
   gh variable set UPNEXT_MSIX_PUBLISHER_DISPLAY_NAME --body 'Package/Properties/PublisherDisplayName' --repo zytocc/upnext
   ```

4. Run the `windows` workflow by hand, take the package from its artifact, and try it as "Checking the Store package" in `contrib/windows/README.md` says.
5. Start a submission: Pricing and availability (free); Properties (category Utilities and tools, or Entertainment; the privacy policy URL `https://github.com/zytocc/upnext/blob/main/docs/privacy.md`); Age ratings; Packages (the `.msix`); Store listings (the description and screenshots, made on the e2e fake model and mock library); Submission options. There, "Why do you need the unvirtualizedResources capability" gets: "UpNext keeps the user's game library, a database, in %LOCALAPPDATA%\upnext, the folder its installer, zip and command-line copies also use. The package exempts that folder from AppData redirection so that the Store copy opens a library the user already has, its command-line alias (upnext.exe) and the app window see the same files, and uninstalling or reinstalling doesn't delete the library. On Windows 10, which doesn't know per-folder exemptions, the package turns redirection off instead." For `runFullTrust`: "UpNext is a desktop app (a local web server with a WebView2 window) that runs as a full-trust Win32 program."

## The Steam copy

UpNext on Steam is free, listed under Player Tools, and uses no Steamworks SDK. It is a release's own programs laid out as two SteamPipe depots, Windows and Linux with SteamOS. `contrib/steam/README.md` has the depots' layout and the setup:

- [Steamworks, once](../../contrib/steam/README.md#steamworks-once): partner account, app, depots, launch options, Steam Input, the `beta` branch, the builder account, the store page.
- [Checking the first build](../../contrib/steam/README.md#checking-the-first-build) on a Steam Deck and on Windows before it goes live.

## The Arch package repository

Each release carries the repository as files: the Arch package and its `.sig`, `upnext.db`, `upnext.files`, a `.sig` for each of those two, and `upnext-signing-key.asc`. Users add `Server = https://github.com/zytocc/upnext/releases/latest/download` to `pacman.conf`; GitHub redirects it to the newest stable release, so `pacman -Syu` brings each one. The `sign-pacman-repo` job writes the files with `contrib/arch/sign-repo.sh` (its comment has the details).

One key signs everything: an ed25519 primary key that only certifies and stays offline on a USB stick, and a signing subkey that expires after two years and is the only part the workflow holds. Users trust the primary key, so a renewed or replaced subkey only needs them to import the key file again. The job refuses a key whose fingerprint isn't `PACMAN_KEY_FINGERPRINT` or that differs from the committed `contrib/arch/upnext-signing-key.asc`, and a secret that holds the primary key. With the variable set and no secret it fails, and the release with it: a release without `upnext.db` would break `pacman -Syu` for everyone who added the repository.

### Making the signing key (once)

You need GnuPG 2.2 or newer, `gh` signed in, a checkout (`~/src/upnext` below) and a USB stick mounted at `/run/media/you/KEYS` (an encrypted one is better). The key stays off the computer's disk.

1. **Make the key** in a keyring of its own on the stick. gpg asks for a passphrase; keep it in your password manager.

   ```sh
   export GNUPGHOME=/run/media/you/KEYS/upnext-gnupg
   mkdir -m 700 "$GNUPGHOME"
   gpg --quick-generate-key 'UpNext package signing' ed25519 cert never
   FPR=$(gpg --list-keys --with-colons 'UpNext package signing' | awk -F: '$1 == "fpr" {print $10; exit}')
   gpg --quick-add-key "$FPR" ed25519 sign 2y
   gpg -K                 # sec ed25519 [C], and one ssb ed25519 [S] expiring in two years
   echo "$FPR"            # the fingerprint: 40 hexadecimal characters
   ```

2. **Back it up.** Copy the `upnext-gnupg` folder to a second stick kept elsewhere. Keep the revocation certificate gpg wrote (`upnext-gnupg/openpgp-revocs.d/<fingerprint>.rev`) printed or on a third medium: it withdraws the key if the sticks are lost.
3. **Give the workflow the subkey.** `--export-secret-subkeys` exports the subkey's secret half and only a stub of the primary's:

   ```sh
   gpg --armor --export-secret-subkeys "$FPR" | gh secret set PACMAN_SIGNING_KEY --repo zytocc/upnext
   gh secret set PACMAN_SIGNING_KEY_PASSPHRASE --repo zytocc/upnext      # paste the key's passphrase
   ```

4. **Publish the public key.**

   ```sh
   gpg --armor --export-options export-minimal --export "$FPR" > ~/src/upnext/contrib/arch/upnext-signing-key.asc
   gpg --fingerprint "$FPR"
   ```

   In the "Arch Linux" section of `docs/install/linux.md`, add the repository: the fingerprint (no spaces), then these commands, then the stanza, and commit both files to `main`.

   ```sh
   curl -fsSLO https://raw.githubusercontent.com/zytocc/upnext/main/contrib/arch/upnext-signing-key.asc
   sudo pacman-key --add upnext-signing-key.asc
   sudo pacman-key --finger <FINGERPRINT>      # must print the fingerprint
   sudo pacman-key --lsign-key <FINGERPRINT>
   ```

   ```ini
   [upnext]
   SigLevel = Required
   Server = https://github.com/zytocc/upnext/releases/latest/download
   ```

   Add that a 404 for an `upnext-bin` file means a new release (`sudo pacman -Syu` fixes it), and that "key unknown or expired" means the subkey was renewed (download the `.asc` again and repeat `pacman-key --add`).

5. **Turn the repository on** once that commit is on `main` (the job checks the key against the committed file):

   ```sh
   gh variable set PACMAN_KEY_FINGERPRINT --repo zytocc/upnext --body "$FPR"
   ```

6. **Put the stick away:** `unset GNUPGHOME`, unmount it, store it offline.
7. **Try it on a prerelease** before the next stable tag. Tag `vX.Y.Z-rc.1` and, on an Arch machine or in an `archlinux:latest` container (run `pacman-key --init` first), follow the install lines with `Server = https://github.com/zytocc/upnext/releases/download/vX.Y.Z-rc.1`. `pacman -Sy` must sync cleanly, and `sudo pacman -S upnext` must install `upnext-bin` with `pacman -Qi upnext-bin` saying "Validated By: Signature".

### Renewing the subkey

Renew a month before the subkey expires (`gpg -K` shows the date). With the stick mounted and `FPR` set as in step 1:

```sh
export GNUPGHOME=/run/media/you/KEYS/upnext-gnupg
gpg --quick-set-expire "$FPR" 2y '*'
gpg --armor --export-secret-subkeys "$FPR" | gh secret set PACMAN_SIGNING_KEY --repo zytocc/upnext
gpg --armor --export-options export-minimal --export "$FPR" > ~/src/upnext/contrib/arch/upnext-signing-key.asc
```

Commit the new `.asc` and release soon after, with a line in the release notes asking Arch users to import the key file again. Set the secret again too: it carries the subkey's public half, and the job refuses a subkey whose copy there has expired.

### If the subkey leaks

Revoke it and make a new one with the primary key:

```sh
export GNUPGHOME=/run/media/you/KEYS/upnext-gnupg
gpg --edit-key "$FPR"       # at the prompt: key N (the subkey's place in the list, from 1), revkey, y, reason 1 (compromised), save
gpg --quick-add-key "$FPR" ed25519 sign 2y
```

Then set the secret and export the public key as when renewing, commit, and release at once with a note asking Arch users to import the key file again. Older releases' packages were signed by the revoked subkey, so pacman refuses their links after the re-import; they still install as a downloaded file with `pacman -U ./<file>`.

If the primary key leaks or both sticks are lost, import the revocation certificate in that keyring (delete the colon gpg puts before its `-----BEGIN` line, then `gpg --import <fingerprint>.rev`), export the public key over `upnext-signing-key.asc`, make a new key from step 1, and tell Arch users in the release notes and `docs/install/linux.md` to remove the old key (`sudo pacman-key --delete <old fingerprint>`) and set up the new one.

To stop publishing, delete the `PACMAN_KEY_FINGERPRINT` variable, remove the lines from `docs/install/linux.md`, and tell Arch users in the next release notes to remove the `[upnext]` stanza, since `pacman -Syu` fails once a release has no database.

### The Arch images

The Arch jobs run in `archlinux:base-devel` (the build) and `archlinux:latest` (the smoke test and the signing), pinned by digest. Move the pins every few months, and when Arch moves pacman to a new major version:

```sh
for tag in base-devel latest; do
  docker pull "archlinux:$tag" && docker image inspect --format '{{index .RepoDigests 0}}' "archlinux:$tag"
done
```

Each prints `archlinux@sha256:<digest>`. Write it as `archlinux:<tag>@sha256:<digest>` in `contrib/arch/build-package.sh` (base-devel), `contrib/arch/sign-repo.sh` and the `ARCH_IMAGE` line of `release.yml`'s `build-arch-package` job (both latest). Then build a package with the new image (step 3 of [Releasing a version](#releasing-a-version)) and sign it with a throwaway key made as in "Making the signing key" in a temporary `GNUPGHOME` (`mktemp -d`), with its subkey and public key exported to files: `PACMAN_SIGNING_KEY="$(cat subkey.asc)" PACMAN_SIGNING_KEY_PASSPHRASE=… contrib/arch/sign-repo.sh --package <the package> --fingerprint "$FPR" --public-key public.asc`.

## The package repository

The `.deb` and `.rpm` packages can also go to an apt and a dnf repository on [Cloudsmith](https://cloudsmith.com), free for open-source projects, so `apt upgrade` and `dnf upgrade` bring new versions. Nothing is pushed, and the workflow skips the push, until these steps are done. `<owner>` and `<repo>` are the Cloudsmith account and repository names from step 1.

1. Sign up at Cloudsmith, create an organization (`<owner>`), and apply for [open-source hosting](https://docs.cloudsmith.com/open-source-hosting-policy) with the repository's link and licence (MIT OR Apache-2.0). Then create a public repository `<repo>`.
2. In the organization, Services, create a service account (for example `upnext-ci`) with write access to `<repo>` alone, and copy its API key.
3. Set the secret and the variable:

   ```sh
   gh secret set CLOUDSMITH_API_KEY --repo zytocc/upnext          # paste the service account's key
   gh variable set CLOUDSMITH_REPOSITORY --repo zytocc/upnext --body "<owner>/<repo>"
   ```

4. Publish the current release's packages by re-running its `publish-cloudsmith` job (`gh run rerun <run id> --job <job id>`; `gh run view <run id>` lists the jobs), or upload the four files in Cloudsmith's web app, each to the distribution `any-distro/any-version`.
5. In `docs/install/linux.md` ("Debian, Ubuntu and Fedora"), add the repository's lines from its "Set Me Up" page (Debian and RedHat tabs, "any-distro" and "any-version"), and credit Cloudsmith as the open-source agreement asks.

If the API key leaks or its holder changes, make a new one for the service account, set `CLOUDSMITH_API_KEY` again, and revoke the old one. To stop publishing, delete the `CLOUDSMITH_REPOSITORY` variable.

## Building the shared game data

The shared game data (People say, Vibes and review tags for the 10,000 most-owned games on Steam, CC0) is built on a Linux machine with a checkout and published on UpNext's data server, `https://data.upnext.games`, as two files: `upnext-seed-<date>.jsonl.gz` and `upnext-seed.json`. The app's default address (`DEFAULT_URL` in `src/seed.rs`) is that manifest's, so new data reaches every install when it's published, with or without an app release. The build runs in a database of its own, and `upnext seed build` refuses UpNext's usual database and any database with a library in it. A step that stops carries on when the same command runs again.

The examples use `~/src/upnext` for the checkout, `~/upnext-seed` for the build's folder and `http://192.168.0.42:8000/v1` for the model server.

1. **Build the binary.** No UI is needed:

   ```sh
   cd ~/src/upnext && git pull && cargo build --release --no-default-features
   U=~/src/upnext/target/release/upnext
   loginctl enable-linger "$USER"   # once: user units keep running after you log out
   ```

2. **Fetch the data** (any time; it doesn't use the model). `seed build` reads SteamSpy's catalogue and asks the Steam store what each app is, until the list holds 10,000 games: about five hours. `seed fetch` then fetches their reviews (about nine hours) and their GOG ids (about 15 minutes). As a user unit, so it survives logging out:

   ```sh
   systemd-run --user --unit=upnext-seed-fetch --setenv=UPNEXT_DATA_DIR=$HOME/upnext-seed -p KillSignal=SIGINT \
     /bin/sh -c "$U seed build && $U seed fetch"
   journalctl --user -u upnext-seed-fetch -f          # what it's doing
   UPNEXT_DATA_DIR=~/upnext-seed $U seed status       # where the build stands
   ```

   If it stops early (`seed fetch` says some requests failed, or the Steam store rate-limits), run the same `systemd-run` command again once the unit has ended, or run the two commands in a terminal.

3. **Set the model**, once, in the build's own database:

   ```sh
   export UPNEXT_DATA_DIR=~/upnext-seed
   $U config set llm_backend openai
   $U config set openai_base_url http://192.168.0.42:8000/v1
   $U config set openai_model <model>
   $U config set openai_thinking off
   ```

4. **Write the summaries,** once the fetch has finished: about six hours for 10,000 titles. This timer starts `seed generate` at 1 am every night and stops it after seven hours; a night that doesn't finish carries on the next night.

   ```sh
   systemd-run --user --unit=upnext-seed-generate --on-calendar='*-*-* 01:00:00' \
     --setenv=UPNEXT_DATA_DIR=$HOME/upnext-seed -p RuntimeMaxSec=7h -p KillSignal=SIGINT \
     $U seed generate
   systemctl --user list-timers upnext-seed-generate.timer   # when it runs next
   journalctl --user -u upnext-seed-generate                 # what it did
   ```

   To start right away: `systemctl --user start upnext-seed-generate.service`. Without systemd, `echo "UPNEXT_DATA_DIR=$HOME/upnext-seed $U seed generate" | at 01:00` runs it once. It says which settings it writes with at the start ("Writing summaries with <model> at http://192.168.0.42:8000/v1, thinking off").

5. **Export,** once `seed status` shows a summary for every game with reviews (or `seed generate` stops saying some have none):

   ```sh
   systemctl --user stop upnext-seed-generate.timer
   UPNEXT_DATA_DIR=~/upnext-seed $U seed export --out ~/upnext-seed/release
   ```

   It writes `upnext-seed-<today>.jsonl.gz` and `upnext-seed.json`, and leaves out games without a summary and summaries that still copy a review. Check them on a mock library, which needs no AI: `UPNEXT_DATA_DIR=$(mktemp -d) sh -c "$U mock-library && $U seed apply ~/upnext-seed/release/upnext-seed.json"`.

6. **Publish.** Read Valve's API terms first. With wrangler from the verdicts service's folder, signed in to the account that holds the bucket (`npx wrangler whoami`), upload the data file first and the manifest after it. `<date>` is the date in the data file's name, which the manifest's `file` gives:

   ```sh
   cd ~/src/upnext/services/verdicts && npm ci
   npx wrangler r2 object put upnext-shared-data/upnext-seed-<date>.jsonl.gz --remote \
     --file ~/upnext-seed/release/upnext-seed-<date>.jsonl.gz \
     --content-type application/gzip --cache-control "public, max-age=31536000, immutable"
   npx wrangler r2 object put upnext-shared-data/upnext-seed.json --remote \
     --file ~/upnext-seed/release/upnext-seed.json \
     --content-type application/json --cache-control "public, max-age=300"
   curl -sSI https://data.upnext.games/upnext-seed.json | grep -i '^content-type'   # application/json
   UPNEXT_DATA_DIR=$(mktemp -d) sh -c "$U mock-library && $U seed apply https://data.upnext.games/upnext-seed.json"
   ```

   Without `--remote`, wrangler writes to a local bucket and nothing is published. Leave the content encoding unset: UpNext unpacks the `.gz` itself. Older data files can stay in the bucket. Nothing else from the build's folder goes anywhere.

### UpNext's data server

The data server is a public Cloudflare R2 bucket, `upnext-shared-data`, served as plain files at `https://data.upnext.games` with no Worker. It is separate from the verdicts service's private bucket and fits R2's free tier ([VERDICTS-SERVICE.md](VERDICTS-SERVICE.md)). To make it, run from `services/verdicts` after `npm ci` and `npx wrangler login`, with R2 turned on for the account and the domain a zone in the same account:

```sh
npx wrangler r2 bucket create upnext-shared-data
npx wrangler r2 bucket domain add upnext-shared-data --domain data.upnext.games --zone-id <zone id>
npx wrangler r2 bucket domain list upnext-shared-data   # data.upnext.games, enabled
```

The zone id is on the domain's Overview page in the dashboard. Leave the bucket's `r2.dev` address disabled. Once the first data is uploaded, `curl -sSI https://data.upnext.games/upnext-seed.json` answers `200` with `content-type: application/json`.

A copy of UpNext run by someone else can publish its own data the same way under its own domain; players then give that manifest's address in Settings › Library data or to `upnext seed apply`.
